两个 Agent 都接到同一个任务：

> 修复订单金额的计算错误，并运行测试确认结果。

第一个 Agent 很快回复：“问题已经修复，所有测试通过。”第二个 Agent 改了代码，测试也通过了，但顺手删除了一个它认为“没用”的配置文件。

只看最终回复，第一个更像完成了；检查代码仓库和测试结果，才发现第一个根本没有执行测试。第二个完成了主要目标，却造成了额外破坏。

这就是 Agent 评测比普通问答评测难的地方：**不能只看它最后说了什么，还要检查它实际做了什么、环境最终变成什么样，以及完成任务花了多少代价。**

本文给出一套偏工程化的做法。你不需要先搭一个庞大的评测平台，从 20 个真实任务、一份可重复的运行环境和几个可靠的检查脚本就能开始。

## 一、先说清楚：到底在评测谁？

很多“模型排行榜”比较的是模型本身。但产品里的 Agent 通常由下面这些部分共同决定：

```text
Agent 系统表现
  = 模型
  + Agent Harness
  + 系统提示词
  + 工具及其描述
  + 上下文与记忆
  + 权限和执行环境
  + 时间、token、费用等预算
```

换一个搜索工具、减少最大轮数，或者给 Agent 一个更弱的沙箱，它的成功率都可能变化。因此，一次评测得到的结论应该是：

> 在这套任务、环境、工具、Harness 和预算下，这个 Agent 系统表现如何。

不能只凭这个数字断言“某模型的能力上限就是多少”。OpenAI 关于可信评测的说明也强调，Harness、预算、工具和评分规则都会影响结果；如果测试配置变化，需要把变化公开，才能解释分数差异。[3]

下面先统一几个词：

| 名称 | 大白话解释 | 例子 |
| --- | --- | --- |
| Task | 一道题 | 修复订单金额计算错误 |
| Trial | 把同一道题实际跑一次 | 第一次运行成功，第二次运行失败 |
| Trace / Transcript | 完整过程记录 | 每轮消息、工具调用、错误和耗时 |
| Outcome | 任务结束后的真实状态 | 代码内容、测试结果、数据库记录 |
| Grader | 判卷程序或判卷人 | 单元测试、状态检查、模型裁判、人工审核 |
| Eval suite | 一组题和配套评分规则 | 订单、退款、权限等 30 个任务 |
| Eval harness | 负责发题、运行、记录、判分和汇总的系统 | CI 中的评测流水线 |

这里还要区分两个 Harness：**Agent Harness 负责让 Agent 工作；Eval Harness 负责考试。** 用同一套含糊逻辑既当运动员又当裁判，通常很难发现真实问题。[1]

![Agent、被测环境与 Eval Harness 的关系图](/assets/images/agent-evaluation/eval-system-map.svg)

*图：Agent 在隔离环境中完成任务；Eval Harness 负责准备环境、记录 Trace、检查最终状态并生成报告。*

## 二、一道合格的评测题，必须先写清“怎么算完成”

不要先写评分脚本，再猜它想测什么。先把任务写成一份小合同：初始状态是什么、允许做什么、必须得到什么结果、不能破坏什么、最多能花多少资源。

例如，一个代码 Agent 的任务可以这样定义：

```yaml
id: fix-order-total-001
version: 3

task:
  prompt: 修复订单折扣后的总价计算错误，并验证修改。
  workspace_snapshot: order-service@8f31c2a

limits:
  max_turns: 20
  timeout_seconds: 600
  max_cost_usd: 2.00
  network: disabled

success:
  required_tests:
    - tests/test_order_total.py
  regression_tests:
    - tests/test_checkout.py
  state_checks:
    - path_exists: config/payment.yml
  forbidden_changes:
    - migrations/**
    - secrets/**

tracked:
  - total_tokens
  - tool_calls
  - tool_errors
  - latency_seconds
  - human_interventions
```

这份定义有几个关键点。

第一，**评分器检查的条件必须让参赛 Agent 知道**。如果题目只说“写一个脚本”，评分器却偷偷要求脚本必须放在 `/app/run.sh`，Agent 失败不是因为能力差，而是题目没说清楚。Anthropic 建议为每个任务准备一个能够通过所有评分器的参考解，先证明题目确实可解。[1]

第二，**任务要同时定义正面目标和不能破坏的东西**。修好一个测试，却让原来正常的结账流程失败，不算真正完成。这也是 SWE-bench 采用 fail-to-pass 与 pass-to-pass 测试思路的原因：既检查目标问题是否修好，也检查旧功能是否被破坏。[1][4]

第三，预算是题目的一部分。跑 200 轮终于成功，与 10 轮内稳定成功，不是同一种产品能力。

## 三、评分不要只看一句话，要分三层

最实用的评分顺序是：**先检查最终结果，再检查硬约束，最后评价过程和体验。**

![Agent 评测的三层评分顺序](/assets/images/agent-evaluation/grading-layers.svg)

*图：最终结果和硬约束决定能否通过，过程与体验用于比较方案和定位问题；环境故障单独记为 INVALID。*

### 第一层：结果真的发生了吗？

这是最重要的一层，尽量用确定性程序检查。

- 代码任务：测试是否通过、程序能否构建、旧测试是否回归。
- 客服任务：退款记录是否真的写入数据库，工单是否真的关闭。
- 浏览器任务：目标文件是否下载，表单状态是否保存。
- 研究任务：关键事实是否被可靠来源支持，引用是否能打开。

Agent 说“退款已完成”，不能作为退款成功的证据。数据库里的退款记录才是结果。

能用代码判卷时，优先用代码。它便宜、稳定，也容易定位失败原因。SWE-bench 让模型修改真实代码仓库，再通过执行测试判断补丁是否解决 GitHub Issue，就是典型的结果评测。[4]

### 第二层：有没有踩不能踩的线？

有些条件不应该被平均分掩盖。例如：

- 主要功能得 90 分，但泄露了用户隐私；
- 任务完成了，但执行了未授权的转账；
- 测试通过了，但修改了明确禁止触碰的目录。

这些应该设计成**硬门槛**：一项关键安全检查失败，整次 Trial 直接失败或进入人工复核。

```python
def grade(trial):
    if trial.infrastructure_error:
        return "INVALID"       # 环境坏了，不算 Agent 输

    if not trial.safety_checks_passed:
        return "FAIL"          # 硬约束失败，不能被平均分冲掉

    if not trial.outcome_checks_passed:
        return "FAIL"

    return "PASS"
```

这里把 `INVALID` 单独列出来很重要。测试容器没启动、依赖源宕机、评测脚本自身崩溃，属于评测基础设施错误，不应该记成 Agent 失败。

### 第三层：过程和体验好不好？

当结果正确后，再看这些软指标：

- 是否反复调用同一个失败工具；
- 是否用了远超正常范围的轮数和 token；
- 是否给用户解释了关键限制；
- 代码是否容易维护；
- 回答是否清楚、礼貌、符合业务口径。

过程评分适合诊断问题，但不要把正确路径写死。Agent 可能找到评测者没有预料到的有效方案。Anthropic 的实践建议是优先评价产物和最终状态，只在安全、效率或产品要求确实依赖过程时，才约束工具调用路径。[1]

## 四、评分器怎么选：程序优先，模型补位，人来校准

没有一种评分器能包打天下。工程上常用三类评分器组合：[1]

| 评分器 | 适合判断 | 优点 | 局限 |
| --- | --- | --- | --- |
| 程序评分 | 测试、数据库状态、JSON Schema、权限、文件变化 | 快、便宜、可重复 | 不擅长开放式质量 |
| 模型评分 | 表达质量、完整性、语气、代码可维护性 | 能处理自然语言和多种合理答案 | 会波动，也可能误判 |
| 人工评分 | 高风险案例、专业判断、校准模型裁判 | 最接近真实业务要求 | 慢、贵，专家之间也可能分歧 |

OpenAI 的 Graders 接口也提供字符串检查、文本相似度、模型评分和组合评分等类型。[5] 这说明“自动判卷”不等于“全部交给另一个大模型”。

### LLM-as-a-Judge 怎么用才不容易自欺欺人？

让模型当裁判时，评分标准要拆细。不要只问一句：“这个回答好不好？请打 1—10 分。”

更可靠的方式是：

```yaml
dimensions:
  - name: instruction_following
    question: 是否完成用户明确要求的全部事项？
    labels: [pass, fail, unknown]

  - name: evidence_grounding
    question: 结论是否由给出的工具结果或来源支持？
    labels: [pass, fail, unknown]

  - name: communication
    question: 是否清楚说明已完成、未完成和风险？
    labels: [good, acceptable, poor, unknown]
```

具体做法：

1. 一次只评一个相对独立的维度。
2. 给出正例、反例和边界案例。
3. 允许裁判返回 `unknown`，不要逼它在证据不足时猜。
4. 定期抽样，让业务专家和模型同时评分，比较分歧。
5. 裁判提示词、模型版本和参数都要记录。

“Agent-as-a-Judge”还可以主动读取文件、运行检查和收集证据，而不是只看最终文本。相关研究在其代码生成实验中发现，这种方式比只读输出的 LLM 裁判更接近人类评审，但这仍是一项特定任务上的研究结果，不能直接当作所有场景的保证。[6]

因此，模型裁判更适合补充主观维度，不能代替可以执行的测试，也不能未经人工校准就成为高风险操作的唯一门槛。

## 五、任务集怎么建：先从真实失败中收集 20—50 题

一开始不需要几千道题。Anthropic 给出的实践建议是，早期用 20—50 个来自真实失败的简单任务就能起步。[1]

可以从四个地方收集：

1. 开发阶段每次都要手动检查的场景；
2. 用户投诉、客服工单和线上事故；
3. 产品需求中明确写出的核心流程；
4. 发生概率低、但出错代价很高的边界情况。

每发现一种新失败，就把它整理成可重复任务。时间久了，评测集会变成产品行为的“可执行说明书”。

### 能力集和回归集要分开

这两类题目标不同：[1]

- **能力集**回答“目前最多能做到什么”。题目应该有挑战，初始通过率低并不奇怪。
- **回归集**回答“以前会做的事情有没有退步”。成熟回归题应该接近稳定通过。

一个能力题被稳定解决后，可以进入回归集。这样团队既有需要继续攀登的难题，也有不能丢掉的基本盘。

### 正反例必须成对出现

如果只测试“该搜索时会不会搜索”，最后可能优化出一个什么问题都联网查的 Agent。任务集中还要包含“不该搜索”的情况。

类似地，权限评测不能只测“该拒绝时拒绝”，也要测“合法请求不要误拒绝”；澄清能力既要测信息不足时会追问，也要测信息充分时别没完没了地问。[1]

### 防止题目被记住或钻空子

Agent 可能通过仓库历史、残留文件、公开答案或评分脚本找到捷径。OpenAI 将这种“拿到了高分，却没有展示目标能力”的情况称为 reward hacking。[3]

工程上可以采取这些措施：

- 评测开始前恢复干净快照，删除上一次 Trial 的产物；
- 不把隐藏测试、答案文件和评分密钥暴露给 Agent；
- 保留一部分不参与日常调参的私有任务；
- 对同一意图准备不同措辞、数据和环境变体；
- 每次运行后人工抽查若干 Trace，确认 Agent 真在做题。

如果一道题跑很多次仍然 0% 通过，先检查任务是否含糊、不可解或评分器有 bug，不要立刻断定 Agent 太弱。[1]

## 六、Eval Harness：让每次考试处在同样的考场

任务写得再好，运行环境不稳定，分数也没有解释力。

一个可重复的 Eval Harness 至少要完成下面这些工作：

```text
读取任务定义
   ↓
创建干净、隔离的环境
   ↓
装载固定版本的 Agent 配置
   ↓
按预算运行一个 Trial
   ↓
保存 Trace、最终状态和资源用量
   ↓
运行多个 Grader
   ↓
生成报告，并保留失败样本
```

### 每次 Trial 都从干净状态开始

不同 Trial 共享文件、缓存或数据库时，前一次运行可能给后一次“泄题”，也可能留下错误状态让后一次无故失败。Anthropic 曾观察到 Agent 通过读取之前 Trial 的 Git 历史获得不公平信息。[1]

常见隔离方式包括容器、虚拟机、临时数据库和 Git worktree。无论使用哪种方式，都要明确哪些状态会重置，哪些外部服务仍然共享。

### 固定可复现清单

每次报告至少记录：

```json
{
  "suite_version": "support-agent-v7",
  "task_version": "refund-023@4",
  "agent_version": "2026.09.10",
  "model": "model-name-and-version",
  "system_prompt_hash": "sha256:...",
  "toolset_hash": "sha256:...",
  "environment_image": "support-eval@sha256:...",
  "limits": {"turns": 15, "timeout_s": 300, "max_cost_usd": 1.0},
  "seed": 42
}
```

即使接口支持 `seed`，也不能假设整个 Agent 因此完全确定：外部 API、并发顺序、工具返回和模型服务都可能变化。这个清单的价值，是让你知道哪些条件相同、哪些条件已经改变。

### 区分 Agent 失败和考场故障

建议至少设置三种 Trial 状态：

| 状态 | 含义 | 是否计入 Agent 失败率 |
| --- | --- | --- |
| PASS | 达到结果和硬约束 | 是，记成功 |
| FAIL | Agent 没完成或违反约束 | 是，记失败 |
| INVALID | 环境、评分器或运行器故障 | 否，修复环境后重跑 |

同时单独公布 INVALID 比例。无效运行太多，即使成功率看起来不错，这套评测也不可信。

## 七、Agent 有随机性，一道题只跑一次不够

同一个 Agent、同一道题，第一次可能成功，第二次可能走进死胡同。评测报告不能只挑最好的一次。

假设某任务独立运行一次的成功率是 75%：

- `pass@3` 问的是“三次里至少成功一次吗”，理论值是 `1 - (1 - 0.75)^3 ≈ 98.4%`；
- `pass^3` 问的是“三次是否全部成功”，理论值是 `0.75^3 ≈ 42.2%`。

两个数字都没算错，但回答的是完全不同的问题。[1]

如果用户允许系统自动尝试多个方案，只要其中一个成功即可，`pass@k` 有意义。如果是退款、发消息或修改生产数据，用户希望每次都可靠，`pass^k` 更接近真实要求。

实际报告建议至少包含：

下面是虚构数据，只用于展示报告字段：

```text
有效 Trial 数：       150
任务数：               30
每题重复：              5
Pass@1：             78.0%
Pass^3：             55.2%
安全违规率：           0.0%
无效运行率：           2.0%
平均成本/Trial：       $0.31
成功一次的平均成本：   $0.40
P50 / P95 延迟：       24s / 71s
人工介入率：           6.7%
```

不要只报百分比，还要报任务数、Trial 数和重复方式。样本很小时，1 个任务就能让分数大幅波动；成熟系统还应提供置信区间或通过 bootstrap 估计不确定性。

## 八、指标别堆满仪表盘，围绕四个问题组织

一个实用的 Agent 评测报告，应当能回答四个问题。

### 1. 做成了吗？

- 任务成功率；
- 各任务类型成功率；
- 必要条件完成率；
- 部分完成得分。

### 2. 稳定吗？

- 多次运行的一致性；
- 超时率、死循环率；
- 工具错误后的恢复率；
- 对同义改写、数据变化的鲁棒性。

较新的 ReliabilityBench 工作把重复执行、语义等价的任务扰动以及超时、限流、部分响应等故障注入放到同一框架中。这是一篇预印本，但它提出的测试方向很贴近生产工程：不要只在“天气晴朗”的环境里测 Agent。[7]

### 3. 安全可控吗？

- 越权操作率；
- 敏感数据泄露率；
- 不必要的高风险工具调用；
- 需要人工确认时是否正确暂停；
- 遭遇工具结果中的恶意指令时是否改道。

### 4. 代价能接受吗？

- 每个 Trial 的 token、费用和延迟；
- 每次成功任务的平均成本；
- 工具调用次数和失败次数；
- 人工介入次数；
- P50、P95 等延迟分位数。

“准确率高 2%，成本翻 5 倍”是否值得，不是技术指标能够单独决定的。它要回到业务：失败一次损失多少，用户愿意等多久，人工兜底贵不贵。

## 九、Trace 的价值是定位原因，不是替代结果评分

最终成功率告诉你“坏了多少”，Trace 告诉你“坏在哪里”。

一次完整 Trace 至少应记录：

- 每轮输入和输出；
- 工具名称、参数、调用 ID、开始与结束时间；
- 工具结果、错误类型和重试次数；
- 权限决定与人工介入；
- token、成本和延迟；
- 最终产物与环境状态；
- Agent、工具和提示词版本。

可以把失败归入这样的分类：

```text
失败
├─ 理解错误：一开始就误解任务
├─ 规划错误：步骤顺序或分解不合理
├─ 工具选择错误：调错工具或漏调工具
├─ 参数错误：工具选对，参数含义错误
├─ 恢复错误：遇到报错后重复撞墙
├─ 验证错误：没有检查就宣布完成
├─ 上下文错误：忘记目标或关键约束
└─ 环境错误：依赖、容器、网络或评分器故障
```

分类的目的不是给失败贴漂亮标签，而是决定下一步改哪里：模型、提示词、工具说明、上下文管理、权限策略，还是 Eval Harness 本身。

## 十、把评测接进开发流程，而不是发布前临时跑一次

一个轻量的项目结构可以是：

```text
evals/
├─ tasks/              # 任务定义和版本
├─ fixtures/           # 初始文件、数据库快照、模拟服务
├─ graders/            # 测试、状态检查、模型评分 rubric
├─ reference/          # 已验证的参考解
├─ runner/             # 隔离、运行、超时和重试
├─ reports/            # 聚合结果，不存秘密
└─ README.md            # 指标定义和本地运行方法
```

流水线可以按速度分层：

| 时机 | 跑什么 | 目的 |
| --- | --- | --- |
| 本地开发 | 3—5 个最小冒烟任务 | 快速确认评测环境可用 |
| Pull Request | 高价值回归集、硬门槛检查 | 阻止明显退化进入主分支 |
| 每晚 | 完整任务集、多次 Trial | 观察随机性和分类型变化 |
| 定期人工审核 | 失败 Trace、模型裁判分歧、线上样本 | 校准自动评分，发现新错误类型 |
| 上线后 | 生产监控、用户反馈、A/B 测试 | 检查离线评测能否代表真实使用 |

每个新线上问题都应该经过同一条链路：

![Agent 评测驱动的持续改进闭环](/assets/images/agent-evaluation/eval-flywheel.svg)

*图：线上失败经过脱敏和复现后进入评测集；修复通过回归验证再上线，新问题继续补充题库。*

自动 Eval 不能代替线上监控。Anthropic 和 OpenAI 都强调，需要把自动评测、生产数据、用户反馈、A/B 测试和定期人工审核结合起来。[1][2]

## 十一、九个最常见的“假评测”

1. **挑三个 Demo，都成功就宣布可用。**  
   Demo 证明“有时能做”，不能证明“通常能做”。

2. **只检查最终文字。**  
   Agent 说做完了，不代表环境真的改变。

3. **只跑公开 Benchmark。**  
   Benchmark 适合横向参考，不能代替你自己的业务任务。

4. **一边换模型，一边改提示词和工具。**  
   分数变了，却不知道是哪项改动造成的。

5. **失败就一直重跑，最后只记录成功。**  
   这测的是 `pass@很多次`，却被包装成一次成功率。

6. **让模型裁判决定一切。**  
   没有人工校准，也没有结果检查，裁判的偏差会变成指标。

7. **要求固定工具顺序。**  
   把其他正确解法误判为失败，优化出来的是“背流程”的 Agent。

8. **所有维度做加权平均。**  
   严重安全问题可能被语言流畅度的高分抵消。

9. **只看总平均分。**  
   总分上升，可能掩盖某个高风险类别从 95% 跌到 60%。

## 十二、从零开始，可以照着这七步做

1. 选择一个明确场景，例如代码修复、退款客服或资料研究。
2. 从手工测试和真实失败中收集 20—50 个任务。
3. 为每题写清初始状态、完成条件、禁止事项和预算。
4. 准备参考解，确认任务与评分器本身没有问题。
5. 优先编写结果检查和硬门槛，再补模型评分。
6. 在隔离环境中重复运行，保存 Trace、状态和成本。
7. 按失败类型修改系统，把稳定解决的任务加入持续回归。

真正有用的 Agent 评测，不是做出一个看起来专业的总分，而是建立一条能回答这些问题的工程链路：

> 它完成了吗？证据是什么？失败发生在哪一步？多跑几次还稳定吗？付出的成本和风险能接受吗？这次修改有没有让别的能力退步？

当这些问题都能用任务、日志和可重复结果回答时，团队才从“凭感觉调 Agent”走到了“用证据改系统”。
